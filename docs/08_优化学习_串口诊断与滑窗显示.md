## 1. 先算一笔"带宽账"：为什么推理只要 537µs，却只有 35 帧/秒？

板端一帧的"货物"清单（82 通道 JustFloat 帧）：

```
每通道 1 个 float32 = 4 字节
82 通道 + 4 字节帧尾 = 82×4 + 4 = 332 字节/帧
```

串口 SCIA 波特率 115200 → 理论极限 $115200/10 = 11520$ 字节/秒（每字节 10 bit：1 起始 + 8 数据 + 1 停止）。

$$帧率上限 = \frac{11520}{332} \approx 34.7\ \text{帧/秒}$$

**实测 35.2 帧/秒 —— 串口利用率 >99%，链路被塞满了。**

而 NPU 推理耗时（CH45）只有 **≈536 µs**（0.000536 s）。

> **结论：瓶颈根本不在"算"，而在"报"。**
> 每秒 11520 字节的出口，要搬运每秒 35×332 ≈ 11600 字节的报表 —— 推理再快也只能排队出货。
>
> 推论：想提高帧率，优先级是 ①提波特率 ②减通道/减数据量，而**不是**继续优化推理。

📌 顺带一个数字感：如果波特率提升到 921600（8 倍），帧率上限 ≈ 278 帧/秒，推理（536µs）将成为新瓶颈。

## 2. "看到尖峰波"的两类根因 —— 一个必须学会的区分

用户观察：**"CH0-31 和 CH46-77 都是尖峰波"**。这句话背后可能有两类完全不同的问题：

| 类型 | 本质 | 典型成因 | 判据 |
|---|---|---|---|
| A. 显示语义问题 | 数据是对的，是"看法"错了 | 每帧内容快速变化（轮换），在时间轴上看着就是跳变 | **把"一帧数据"单独取出来画成曲线，形状正常** |
| B. 数据 bug | 数据本身就是错的 | 计算/传参错误 | **单帧曲线也不成形**（幅度不对、形状不对） |

**诊断铁律：先看"单帧"，再看"时间轴"。**

- 时间轴（VOFA 默认视图）回答"这个通道随时间怎么变"；
- 单帧（把 CH0..31 当作一条曲线的 32 个点）才回答"这一帧的波形长什么样"。

本次事件里，**两类问题同时存在**：

1. **CH0-31（输入窗）**：单帧形状完全正确（正弦/方波/三角/锯齿），但固件**每帧切换一类波形**（35 fps 下每类每秒切换 ~8.8 次）→ 时间轴上每个通道"乱跳" → 看着像尖峰。**属于 A。**
2. **CH46-77（重建正弦）**：单帧曲线也不对（几乎平坦，全部挤在 −1 附近）→ **属于 B，是真 bug**（见第 3 节）。

## 3. 指针偏移 bug 的教训："布局契约"与"数值反推法"

### 3.1 事实

模型输出是 11 维的 **concat 单张量**：

```
g_out = [ logits×5 | 参数×6 ]
         ↑ 索引 0..4   ↑ 索引 5..10 (A', k', cosφ', sinφ', off', duty')
```

C 端 `params_to_phys(const float *p, ...)` 的契约是"**p[0..5] 即六个参数**"，
但调用处写成了 `params_to_phys(g_out, ...)` —— **忘了偏移 5**。
于是 A/k/cos/sin/off/duty 全部读到了 logits 的值。

### 3.2 症状为什么是"几乎平坦的 −1 附近曲线"？

用具体数字感受（以某帧为例）：

- logits = `[0.016, −0.062, 0.062, −0.328, −0.453]`
- 错读为：A = 0.016×0.8+0.2 = **0.213**（真值 0.89）
  k = −0.062×3.5+0.5 = **0.283**（真值 ~1.4，32 点内只转约 51°，几乎看到一小段弧）
  off = −0.453×0.6−0.3 = **−0.572**（真值 −0.01）
- 预测重建起点：$0.213\times\sin(4.22) - 0.572 = -0.760$

**实测该帧 rec[0] = −0.760 —— 逐位命中**。这就是定位 bug 的决定性证据。

### 3.3 方法论：**"用错误参数手算预测，再看实测是否命中"**

- 如果命中 → 说明"代码逻辑没错，但**喂进去的数据**错了" → 查**通道/指针/索引**；
- 如果不命中 → 说明公式/实现本身错了 → 查**算法**。

这个方法不需要调试器、不需要烧写，纯用"串口数据 + 手算"就能把 bug 逼到墙角。

### 3.4 教训清单

1. **拼接张量要吃透布局**：`[A|B]` 的偏移量是硬编码契约，注释里要写清楚（本次已在代码中留警告注释）。
2. **同一数据流，两处用法可能只有一处错**：CH37-42 用 `g_out[5..10]` 发送是**对的**（显式索引），而函数调用忘了偏移——**发送通道看着正常，不代表下游计算用的是同一组数**。
3. **防御性写法**：要么传 `g_out + 5`，要么函数签名明确写成 `params_to_phys(const float *params6, ...)` 并在文档注明"指向 6 参数起点"。

## 4. 滑窗流式化：把"快照轮换"改成"连续流动"

### 4.1 问题回顾（显示语义问题）

原设计：每帧在"4 类波形"之间轮换，**每帧的窗内容都是全新的一帧快照**。
时间轴上：每个通道 = "每帧取同一位置的采样、但波形在换" → 全是跳变。

### 4.2 滑窗设计

把窗想象成"一条连续长信号上开的一扇 32 点窗口"，**每帧把窗整体向右滑 1 个样本点**：

```
第 f 帧的窗:  长信号[ f : f+32 ]
窗内第 n 点:  in[n] = shape( θ(f) + Δ·n ),   Δ = 2π·k/32
每帧推进:      θ(f+1) = θ(f) + Δ
```

- **θ 是"长信号"的相位**；Δ 是窗内相邻两点间的相位差（由该类的周期数 k 决定）。
- 这样第 f+1 帧的窗 = 第 f 帧窗"整体左移 1 点、右端补 1 点新波形"——**连续、不跳变**。

**周期验证**（用实测数字）：k=2 的正弦类，每帧转 $2π×2/32 = 22.5°$，
转满一圈需要 $360/22.5 = 16$ 帧 —— 实测 CH0 序列周期正好 16 帧 ✓。

### 4.3 为什么"每个通道"都有波形了？

时间轴上，CH0 的取值序列 = `长信号[f]`（f 递增）——**就是长信号本身**！
CH1 = `长信号[f+1]`（比 CH0 滞后 1 个样本）……32 个通道 = 同一长信号的 32 个"相位切片"。

于是 VOFA 时间轴上，每条曲线都是**连续波形**（彼此微错相），完全消除了"尖峰跳变"的观感。

### 4.4 工程细节（都来自实测）

| 细节 | 做法 | 原因 |
|---|---|---|
| 换类策略 | 每类保持 256 帧（~7.3s），然后切下一类 | 保证观察时长；避免高频切换 |
| 换类复位 | θ 重置为该类的初始相位 CASE_PHI | 每类从"标准相位"开始，与 golden 样本同口径 |
| θ 限幅 | `if (theta ≥ 2π) theta -= 2π` | float 长时间累加会损失精度；所有波形以 2π 为周期，模 2π 等价 |
| 每帧推理 | 窗每帧都在变 → 每帧都推理（536µs ≤ 28ms 帧周期，完全来得及） | 参数/分类必须跟随当前窗 |

### 4.5 副作用（如实记录）

滑窗中"折点位置"会扫过窗内不同位置。实测 **triangle 类**在某些相位下置信度降到 0.88（约 2.5% 的帧），极少数帧跌到 0.5。
这属于"训练分布边缘的窗"，分类主体仍正确，不影响演示功能；报告见 09。

## 5. 顺手的两个硬件/工程优化

1. **TMU 硬件加速**：编译选项 `--fp_mode=relaxed` 让 `sinf/atan2f/除法` 走 F28P55 的 TMU 硬件单元（此前被 `advice #2614-D` 提示）。
   - 本应用里 C 端"参数→正弦"每帧要算 32 次 `sinf`，收益直接。
   - 精度：TMU 三角函数误差远小于本项目输出分辨率，golden 自检不经过它们（比对的是 NPU 输出），无风险。
2. **死代码清理**：saw2sin 时代的手写推理 `hand_infer.c/h` 已无引用（从工程排除编译），减少体积和混淆。

- `torch` 环境：`import matplotlib.pyplot` 正常，但 `plt.subplots()→savefig` **原生崩溃**（Python 都抓不住的段错误级）。

- 一个环境干一件事更稳：**训练环境（torch）负责训练/推理；工具环境（ti-npu）负责板端工具链与画图**。
